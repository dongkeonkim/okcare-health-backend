# 오케어 백엔드 기능 명세

## 기준

구현 기술과 무관하게 API와 테스트로 관찰할 수 있는 입력, 출력, 상태 변화와 예외 정책을 기록한다.

## 1. 문서 목적

이 문서는 오케어 백엔드가 외부에 제공해야 하는 기능과 동작 규칙을 정의한다. 서비스의 배경과 목표는 [`비즈니스_기획.md`](../요구사항/비즈니스_기획.md), 기술 구현과 검증 방법은 [`개발_계획.md`](../설계/개발_계획.md)를 따른다.

문서에 없는 기능, 상태 전이와 대체 흐름은 구현하지 않는다. 기능 정책을 변경할 때는 이 문서를 먼저 갱신하고 사용자 승인을 받는다.

## 2. 기능 범위

서비스의 포함·제외 범위는 [`비즈니스_기획.md`](../요구사항/비즈니스_기획.md)를 기준으로 한다. 이 문서는 다음 기능의 외부 동작을 정의한다.

- 이름, 닉네임, 이메일과 비밀번호를 사용한 회원가입
- 이메일과 비밀번호를 사용한 로그인
- 액세스 토큰 재발급과 로그아웃
- 삼성헬스와 Apple Health 형식의 건강 데이터 저장
- 동일 데이터 재전송에 대한 멱등 처리
- 인증 회원과 `recordkey`의 소유권 연결
- `recordkey`별 Daily/Monthly 집계 조회
- 일관된 검증 및 오류 응답
- 리프레시 토큰 저장소와 조회 캐시의 장애 처리

## 3. 공통 API 규칙

- API 기본 경로는 `/api/v1`이다.
- 보호된 API는 `Authorization: Bearer {accessToken}` 헤더가 필요하다.
- JSON 요청은 신뢰 경계에서 검증한다.
- 날짜와 월 범위의 `from`, `to`는 모두 포함한다.
- `from`이 `to`보다 이후이면 `400 Bad Request`를 반환한다.
- 다른 회원이 소유한 `recordkey`는 `403 Forbidden`을 반환한다.
- 존재하지 않는 회원 또는 `recordkey`는 `404 Not Found`를 반환한다.
- 회원이 소유한 `recordkey`에 조회 기간의 데이터가 없으면 `200 OK`와 빈 `items`를 반환한다.

## 4. 회원과 인증

### 4.1 회원가입

```http
POST /api/v1/auth/signup
Content-Type: application/json
```

```json
{
  "name": "홍길동",
  "nickname": "길동",
  "email": "gildong@example.com",
  "password": "StrongPassword1!"
}
```

```json
{
  "id": 1,
  "name": "홍길동",
  "nickname": "길동",
  "email": "gildong@example.com"
}
```

- 이름, 닉네임, 이메일과 비밀번호는 필수다.
- 이메일은 앞뒤 공백을 제거하고 소문자로 정규화한다.
- 정규화한 이메일은 회원 간에 중복될 수 없다.
- 비밀번호는 응답이나 로그에 노출하지 않는다.
- 이메일 중복은 `409 Conflict`를 반환한다.
- 비밀번호의 상세 길이와 문자 조합 규칙은 인증 구현 전에 사용자 승인을 받아 이 문서에 추가한다.

### 4.2 로그인

```http
POST /api/v1/auth/login
Content-Type: application/json
```

```json
{
  "email": "gildong@example.com",
  "password": "StrongPassword1!"
}
```

```json
{
  "tokenType": "Bearer",
  "accessToken": "...",
  "accessTokenExpiresIn": 900,
  "refreshToken": "...",
  "refreshTokenExpiresIn": 1209600
}
```

- 액세스 토큰 유효시간은 15분이다.
- 리프레시 토큰 유효시간은 14일이다.
- 로그인 실패 응답은 이메일 존재 여부를 노출하지 않는다.
- 리프레시 토큰을 저장할 수 없으면 로그인을 실패 처리한다.

### 4.3 토큰 재발급

```http
POST /api/v1/auth/refresh
Content-Type: application/json
```

- 유효한 리프레시 토큰을 새 액세스 토큰과 리프레시 토큰으로 교체한다.
- 교체가 성공하면 기존 리프레시 토큰은 즉시 사용할 수 없어야 한다.
- 만료, 위조, 폐기된 토큰은 `401 Unauthorized`를 반환한다.
- 토큰 교체를 완료할 수 없으면 재발급을 실패 처리한다.

### 4.4 로그아웃

```http
POST /api/v1/auth/logout
Authorization: Bearer {accessToken}
Content-Type: application/json
```

- 로그아웃은 전달된 리프레시 토큰을 폐기한다.
- 폐기된 리프레시 토큰은 재발급에 사용할 수 없다.
- 이미 발급된 액세스 토큰은 자체 만료 시각까지 서명과 만료 검증을 통과하면 사용할 수 있다.

## 5. 건강 데이터

### 5.1 입력 형식

```http
POST /api/v1/health-data
Authorization: Bearer {accessToken}
Content-Type: application/json
```

요청 본문은 [`../../fixtures/health`](../../fixtures/health)의 `INPUT_DATA*.json` 구조를 그대로 받는다.

- SamsungHealth의 `steps`는 JSON number다.
- Health Kit의 `steps`는 정수 또는 소수를 나타내는 JSON string이다.
- calories 단위는 `kcal`, distance 단위는 `km`만 허용한다.
- 공급자가 전송한 `vender` 필드명은 오탈자를 포함한 원본 계약으로 취급한다.
- 필수 필드 누락, 지원하지 않는 단위와 파싱할 수 없는 값은 `400 Bad Request`를 반환한다.

### 5.2 시간과 숫자 정규화

- 삼성헬스의 타임존 없는 시각은 `Asia/Seoul`로 해석한다.
- Apple Health의 오프셋 시각은 요청에 포함된 오프셋을 적용한다.
- 모든 절대 시각은 UTC로 정규화한다.
- Daily/Monthly 집계는 `Asia/Seoul`을 기준으로 한다.
- 시작과 종료가 같은 삼성헬스 레코드는 버리지 않고 시작 시각의 날짜에 포함한다.
- 걸음수, 칼로리와 거리는 소수 정밀도를 보존해 처리한다.
- 걸음수는 집계를 마친 후 `HALF_UP`으로 정수 반올림한다.
- 칼로리와 거리는 집계를 마친 후 소수점 여섯 자리로 `HALF_UP` 반올림한다.
- Apple Health의 calories 0은 유효한 원본 값으로 보존한다.

### 5.3 `recordkey` 소유권

- 인증된 회원이 처음 데이터를 전송하면 요청의 `recordkey`를 해당 회원에게 연결한다.
- 이미 다른 회원에게 연결된 `recordkey`의 저장 요청은 `409 Conflict`를 반환한다.
- 이후 저장 및 조회는 연결된 회원에게만 허용한다.

### 5.4 멱등 저장

같은 `recordkey`에서 지표 종류, 측정 시작 시각과 종료 시각이 모두 같으면 동일한 레코드로 판단한다.

- 동일 식별자와 동일 값이 다시 들어오면 `duplicated`로 처리한다.
- 동일 식별자의 측정값이 변경되면 최신 요청 값으로 갱신하고 `updated`로 처리한다.
- 동일 입력 재전송만으로 저장 레코드 수가 증가해서는 안 된다.

저장 응답은 다음 형식을 사용한다.

```json
{
  "recordKey": "7836887b-b12a-440f-af0f-851546504b13",
  "received": 1066,
  "inserted": 1066,
  "updated": 0,
  "duplicated": 0
}
```

## 6. 집계 조회

### 6.1 Daily

```http
GET /api/v1/health-data/daily?recordKey={recordKey}&from=2024-11-01&to=2024-12-31
Authorization: Bearer {accessToken}
```

```json
{
  "recordKey": "7836887b-b12a-440f-af0f-851546504b13",
  "zoneId": "Asia/Seoul",
  "items": [
    {
      "date": "2024-11-15",
      "steps": 7243,
      "calories": 289.209952,
      "distance": 5.419490
    }
  ]
}
```

- `from`, `to`는 `yyyy-MM-dd` 형식이다.
- 날짜별 결과는 오래된 날짜부터 정렬한다.

### 6.2 Monthly

```http
GET /api/v1/health-data/monthly?recordKey={recordKey}&from=2024-11&to=2024-12
Authorization: Bearer {accessToken}
```

```json
{
  "recordKey": "7836887b-b12a-440f-af0f-851546504b13",
  "zoneId": "Asia/Seoul",
  "items": [
    {
      "month": "2024-11",
      "steps": 124783,
      "calories": 5002.499439,
      "distance": 94.342095
    }
  ]
}
```

- `from`, `to`는 `yyyy-MM` 형식이다.
- 월별 결과는 오래된 월부터 정렬한다.

### 6.3 조회 가용성

- 조회 캐시 장애가 발생해도 영속 저장된 데이터를 기준으로 정상 조회를 제공한다.
- 캐시 장애 여부에 따라 응답 형식과 집계값이 달라져서는 안 된다.

## 7. 오류 응답

```json
{
  "code": "HEALTH_RECORD_KEY_FORBIDDEN",
  "message": "접근할 수 없는 recordkey입니다.",
  "fieldErrors": [],
  "traceId": "7a9f...",
  "timestamp": "2024-12-17T01:23:45Z"
}
```

| 상황 | HTTP 상태 |
|---|---:|
| 요청 형식·검증 오류 | 400 |
| 로그인 필요·토큰 오류 | 401 |
| 다른 회원의 `recordkey` 조회 | 403 |
| 회원 또는 `recordkey` 없음 | 404 |
| 이메일·`recordkey` 연결 충돌 | 409 |
| 예상하지 못한 서버 오류 | 500 |

오류 코드와 메시지는 HTTP 상태의 의미와 일치해야 한다. 오류 응답에는 비밀번호, 토큰, 개인 식별 정보와 전체 건강 데이터 요청을 포함하지 않는다.
