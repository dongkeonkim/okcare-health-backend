# 오케어 백엔드 기능 명세

## 1. 문서 목적

이 문서는 구현 기술과 무관하게 API와 테스트로 관찰할 수 있는 입력, 출력, 상태 변화, 예외 정책과
회귀 기준을 정의합니다. 서비스 범위는 [`비즈니스_기획.md`](../요구사항/비즈니스_기획.md), 구현과 검증 방법은
[`개발_계획.md`](../설계/개발_계획.md)을 따릅니다.

## 2. 기능 범위

서비스의 포함·제외 범위는 [`비즈니스_기획.md`](../요구사항/비즈니스_기획.md)를 따릅니다. 외부 계약은
회원·인증, 건강 데이터 저장, Daily/Monthly 조회와 오류·장애 처리 절에서 구체화합니다.

## 3. 공통 API 규칙

- API 기본 경로는 `/api/v1`입니다.
- 보호된 API는 `Authorization: Bearer {accessToken}` 헤더가 필요합니다.
- JSON 요청은 신뢰 경계에서 검증합니다.
- 날짜와 월 범위의 `from`, `to`는 모두 포함합니다.
- `from`이 `to`보다 이후이면 `400 Bad Request`를 반환합니다.
- 조회에서 `recordkey`가 없는 경우와 다른 회원이 소유한 경우는 같은 `404 Not Found`를 반환하고
  `code`, `message`, `fieldErrors`가 같습니다. `traceId`와 `timestamp`는 요청마다 달라지므로 같지 않습니다.
- 조회 응답은 요청 범위의 모든 날짜와 월을 포함하고, 데이터가 없는 구간은 측정값을 `0`으로 채웁니다.
  따라서 데이터가 없는 구간과 측정값이 실제로 `0`인 구간은 응답에서 구분되지 않습니다.

## 4. 회원과 인증

### 4.1 회원가입

```http
POST /api/v1/auth/signup
Content-Type: application/json
```

```json
{
  "name": "홍길동",
  "nickname": "길동",
  "email": "gildong@example.com",
  "password": "StrongPassword1!"
}
```

```json
{
  "id": 1,
  "name": "홍길동",
  "nickname": "길동",
  "email": "gildong@example.com"
}
```

- 이름, 닉네임, 이메일과 비밀번호는 필수입니다.
- 이름과 닉네임은 50자, 이메일은 255자를 넘을 수 없습니다.
- 이메일은 앞뒤 공백을 제거한 뒤 표준 이메일 형식인지 검증하고 소문자로 정규화합니다.
- 정규화한 이메일은 회원 간에 중복될 수 없습니다.
- 비밀번호는 8자 이상 64자 이하이며 영문자와 숫자를 각각 하나 이상 포함합니다.
- 비밀번호는 응답이나 로그에 노출하지 않습니다.
- 가입에 성공하면 `201 Created`를 반환합니다.
- 이메일 중복은 `409 Conflict`를 반환합니다.

### 4.2 로그인

```http
POST /api/v1/auth/login
Content-Type: application/json
```

```json
{
  "email": "gildong@example.com",
  "password": "StrongPassword1!"
}
```

```json
{
  "tokenType": "Bearer",
  "accessToken": "...",
  "accessTokenExpiresIn": 900,
  "refreshToken": "...",
  "refreshTokenExpiresIn": 1209600
}
```

- 액세스 토큰 유효시간은 15분입니다.
- 리프레시 토큰 유효시간은 14일입니다.
- 이메일은 회원가입과 같은 규칙으로 정규화하므로 대소문자와 앞뒤 공백만 다른 값으로도 로그인할 수
  있습니다.
- 이메일 형식과 비밀번호 구성은 검증하지 않고 자격 증명 일치 여부로만 판정합니다.
- 등록되지 않은 이메일과 일치하지 않는 비밀번호는 같은 `401 Unauthorized` 응답을 반환합니다.
- 로그인 실패 응답은 이메일 존재 여부를 노출하지 않습니다.
- 리프레시 토큰을 저장할 수 없으면 로그인을 실패 처리합니다.
- 로그인은 이미 발급된 리프레시 토큰을 폐기하지 않습니다.

### 4.3 토큰 재발급

```http
POST /api/v1/auth/refresh
Content-Type: application/json
```

```json
{
  "refreshToken": "..."
}
```

응답은 액세스·리프레시 토큰과 각 만료 시간을 담는 [로그인 응답](#42-로그인)과 같은 형식입니다.

- 유효한 리프레시 토큰을 새 액세스 토큰과 리프레시 토큰으로 교체합니다.
- 리프레시 토큰만으로 재발급하며 액세스 토큰을 요구하지 않습니다.
- 액세스 토큰은 재발급에 사용할 수 없습니다.
- 교체가 성공하면 기존 리프레시 토큰은 즉시 사용할 수 없어야 합니다.
- 만료, 위조, 폐기된 토큰은 `401 Unauthorized`를 반환하며 세 경우를 구별하지 않습니다.
- 재발급한 리프레시 토큰의 유효시간은 다시 14일입니다. 절대 세션 상한을 두지 않으므로 계속
  재발급하는 클라이언트는 로그아웃할 때까지 로그인 상태를 유지합니다.
- 토큰 교체를 완료할 수 없으면 재발급을 실패 처리합니다.

### 4.4 로그아웃

```http
POST /api/v1/auth/logout
Authorization: Bearer {accessToken}
Content-Type: application/json
```

```json
{
  "refreshToken": "..."
}
```

- 로그아웃은 전달된 리프레시 토큰을 폐기합니다.
- 폐기된 리프레시 토큰은 재발급에 사용할 수 없습니다.
- 이미 발급된 액세스 토큰은 자체 만료 시각까지 서명과 만료 검증을 통과하면 사용할 수 있습니다.
- 성공하면 `204 No Content`를 반환하며 응답 본문이 없습니다.
- 액세스 토큰이 없거나 유효하지 않으면 `401 Unauthorized`를 반환합니다.
- 전달된 리프레시 토큰이 인증된 회원의 것이 아니면 `401 Unauthorized`를 반환합니다.
- 이미 폐기된 리프레시 토큰을 다시 전달해도 성공으로 처리합니다.
- 폐기를 완료할 수 없으면 로그아웃을 실패 처리합니다.

## 5. 건강 데이터

### 5.1 입력 형식

```http
POST /api/v1/health-data
Authorization: Bearer {accessToken}
Content-Type: application/json
```

요청 본문은 [`../../fixtures/health`](../../fixtures/health)의 `INPUT_DATA*.json` 구조를 그대로 받습니다.

**필드 형식**

- 요청 본문의 `recordkey`는 36자 문자열이며, 저장 응답과 조회 파라미터는 `recordKey`를 사용합니다.
- `lastUpdate`는 `yyyy-MM-dd HH:mm:ss Z` 형식입니다.
- 삼성헬스의 측정 구간은 `yyyy-MM-dd HH:mm:ss`, Health Kit의 측정 구간은
  `yyyy-MM-dd'T'HH:mm:ssZ` 형식입니다.
- SamsungHealth의 `steps`는 JSON number이고, Health Kit의 `steps`는 정수 또는 소수를 나타내는
  JSON string입니다.
- `calories` 단위는 `kcal`, `distance` 단위는 `km`만 허용합니다.
- 공급자가 전송한 `vender` 필드명은 오탈자를 포함한 원본 계약으로 취급합니다.

**필수 필드**

- `data.source.name`, `data.source.mode`, `data.source.product.name`,
  `data.source.product.vender`는 필수입니다.
- 각 엔트리의 `period.from`, `period.to`, `steps`, `calories.value`, `calories.unit`,
  `distance.value`, `distance.unit`은 필수입니다.
- `data.entries`는 비어 있을 수 없습니다.

**검증·정규화**

- 공급자는 `data.source.name`으로 판별하며 `SamsungHealth`와 `Health Kit` 외에는
  `400 Bad Request`를 반환합니다.
- 최상위 `type`은 앞뒤 공백을 제거하고 소문자로 정규화하며, `steps`가 아니면
  `400 Bad Request`를 반환합니다.
- 필수 필드 누락, 지원하지 않는 단위와 파싱할 수 없는 값은 `400 Bad Request`를 반환합니다.

**저장 범위·결과**

- `data.memo`와 `data.source.type`은 저장하지 않습니다.
- 저장에 성공하면 `200 OK`와 수신·삽입·갱신·중복 건수를 담는
  [멱등 저장 응답](#54-멱등-저장)을 반환합니다.

### 5.2 시간과 숫자 정규화

- 삼성헬스의 타임존 없는 시각은 `Asia/Seoul`로 해석합니다.
- Apple Health의 오프셋 시각은 요청에 포함된 오프셋을 적용합니다.
- 모든 절대 시각은 UTC로 정규화합니다.
- Daily/Monthly 집계는 `Asia/Seoul`을 기준으로 합니다.
- 시작과 종료가 같은 삼성헬스 레코드는 버리지 않고 시작 시각의 날짜에 포함합니다.
- 걸음수, 칼로리와 거리는 소수점 열두 자리까지 보존하고 그 뒤는 `HALF_UP`으로 반올림해 저장합니다.
- 걸음수는 집계를 마친 후 `HALF_UP`으로 정수 반올림합니다.
- 칼로리와 거리는 집계를 마친 후 소수점 여섯 자리로 `HALF_UP` 반올림합니다.
- 측정값의 정수부는 열두 자리를 넘을 수 없고, 넘으면 `400 Bad Request`를 반환합니다.
- Apple Health의 calories 0은 유효한 원본 값으로 보존합니다.

### 5.3 `recordkey` 소유권

- 인증된 회원이 처음 데이터를 전송하면 요청의 `recordkey`를 해당 회원에게 연결합니다.
- 이미 다른 회원에게 연결된 `recordkey`의 저장 요청은 `409 Conflict`를 반환합니다.
- 이후 저장 및 조회는 연결된 회원에게만 허용합니다.

### 5.4 멱등 저장

같은 `recordkey`에서 지표 종류, 측정 시작 시각과 종료 시각이 모두 같으면 동일한 레코드로 판단합니다.

- 동일 값은 [시간과 숫자 정규화](#52-시간과-숫자-정규화)에 따라 소수점 열두 자리로 맞춘 측정값과
  단위를 기준으로 판정합니다. 저장 정밀도 뒤의 자리만 다른 두 요청은 같은 값으로 봅니다.
- 동일 식별자와 동일 값이 다시 들어오면 `duplicated`로 처리합니다.
- 동일 식별자의 측정값이 변경되면 최신 요청 값으로 갱신하고 `updated`로 처리합니다.
- 동일 입력 재전송만으로 저장 레코드 수가 증가해서는 안 됩니다.
- 한 요청 안에 같은 식별자가 여러 번 들어오면 마지막 항목을 저장하고, 그 식별자는 하나의 결과로만
  계산합니다.
- `received`는 요청에 담긴 엔트리 수를 그대로 반환하므로
  `inserted + updated + duplicated`가 `received`보다 작을 수 있습니다.

저장 응답은 다음 형식을 사용합니다.

```json
{
  "recordKey": "7836887b-b12a-440f-af0f-851546504b13",
  "received": 1066,
  "inserted": 1066,
  "updated": 0,
  "duplicated": 0
}
```

## 6. 집계 조회

### 6.1 Daily

```http
GET /api/v1/health-data/daily?recordKey={recordKey}&from=2024-11-01&to=2024-12-31
Authorization: Bearer {accessToken}
```

```json
{
  "recordKey": "7836887b-b12a-440f-af0f-851546504b13",
  "zoneId": "Asia/Seoul",
  "items": [
    {
      "date": "2024-11-15",
      "steps": 7243,
      "calories": 289.209952,
      "distance": 5.419490
    }
  ]
}
```

- `from`, `to`는 `yyyy-MM-dd` 형식입니다.
- 날짜별 결과는 오래된 날짜부터 정렬합니다.
- 조회 범위가 366일을 넘으면 `400 Bad Request`를 반환합니다. 데이터가 없는 날짜까지 채워 응답하므로
  상한이 없으면 응답 크기를 요청이 정합니다.

### 6.2 Monthly

```http
GET /api/v1/health-data/monthly?recordKey={recordKey}&from=2024-11&to=2024-12
Authorization: Bearer {accessToken}
```

```json
{
  "recordKey": "7836887b-b12a-440f-af0f-851546504b13",
  "zoneId": "Asia/Seoul",
  "items": [
    {
      "month": "2024-11",
      "steps": 124783,
      "calories": 5002.499439,
      "distance": 94.342095
    }
  ]
}
```

- `from`, `to`는 `yyyy-MM` 형식입니다.
- 월별 결과는 오래된 월부터 정렬합니다.
- 조회 범위가 24개월을 넘거나 `yyyy-MM-dd`처럼 일자를 포함하면 `400 Bad Request`를 반환합니다.

### 6.3 조회 가용성

- 조회 캐시 장애가 발생해도 영속 저장된 데이터를 기준으로 정상 조회를 제공합니다.
- 캐시 장애 여부에 따라 응답 형식과 집계값이 달라져서는 안 됩니다.

## 7. 오류 응답

```json
{
  "code": "HEALTH_RECORD_KEY_NOT_FOUND",
  "message": "조회할 수 없는 recordkey입니다.",
  "fieldErrors": [],
  "traceId": "7a9f...",
  "timestamp": "2024-12-17T01:23:45Z"
}
```

| 상황 | HTTP 상태 |
|---|---:|
| 요청 형식·검증 오류 | 400 |
| 로그인 필요·토큰 오류 | 401 |
| 허용되지 않는 HTTP 메서드 | 405 |
| 지원하지 않는 `Content-Type` | 415 |
| `recordkey` 조회 불가(없음과 남의 것 공통) | 404 |
| 이메일·`recordkey` 연결 충돌 | 409 |
| 리프레시 토큰 저장·교체·폐기 실패 | 500 |
| 예상하지 못한 서버 오류 | 500 |

오류 코드와 메시지는 HTTP 상태의 의미와 일치해야 합니다. 오류 응답에는 비밀번호, 토큰, 개인 식별 정보와 전체 건강 데이터 요청을 포함하지 않습니다.
