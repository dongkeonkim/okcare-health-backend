# LLM 코드 리뷰 가이드

## 목적

LLM 코드 리뷰는 변경의 위험을 근거와 함께 찾아 사람의 판단을 돕는 절차다. 승인과 책임은 사람에게 있으며, 리뷰 품질은 코멘트 수가 아니라 중요한 결함의 발견, 근거의 정확성, 낮은 잡음으로 판단합니다.

## 원칙

1. **요구사항 우선** — 사용자 요청과 승인된 범위, [`과제_원문.md`](../요구사항/과제_원문.md), [`비즈니스_기획.md`](../요구사항/비즈니스_기획.md), [`기능_명세.md`](../명세/기능_명세.md), [`개발_계획.md`](../설계/개발_계획.md)를 기준으로 판단하고 문서에 없는 정책을 만들지 않습니다.
2. **변경과 맥락 검토** — 작성자가 아니라 변경을 검토하고, 필요한 호출 경로·설정·스키마·테스트까지 확인합니다.
3. **증거 우선** — 발견 사항에 위치, 발생 조건, 영향과 근거를 제시합니다. 인과관계를 설명할 수 없으면 결함으로 단정하지 않습니다.
4. **불확실성 공개** — 확인한 사실, 추론, 질문과 제안을 구분하고 심각도와 확신도를 별도로 표시합니다.
5. **반증 후 보고** — 다른 계층의 방어, 프레임워크 보장, DB 제약조건과 테스트를 확인해 거짓 양성을 제거합니다.
6. **위험 우선순위** — 요구사항·정확성, 보안·데이터 정합성, 장애, 성능, 유지보수 순으로 보되 실제 영향에 따라 조정합니다.
7. **최소 범위와 낮은 잡음** — 같은 원인은 묶고 취향과 자동화 가능한 스타일 문제를 제외하며, 관련 없는 리팩터링과 기능 확장을 요구하지 않습니다.

리뷰 요청은 기본적으로 검토와 보고만 수행합니다. 발견 사항이 없으면 억지로 만들지 않고, 확인하지 못한 범위와 잔여 위험을 밝힙니다.

## 보고

발견 사항을 심각도순으로 먼저 적고 각 항목에 다음을 포함합니다.

```text
[심각도 / 확신도] 제목
- 위치:
- 발생 조건과 영향:
- 근거:
- 최소 대응:
```

그 뒤에 필요한 질문, 실행한 검증과 잔여 위험을 기록합니다.
