# 오케어 백엔드 테스트 작성 가이드

## 1. 문서 목적

이 문서는 오케어 백엔드 테스트 코드의 공통 작성 원칙을 정의한다.

기대 동작과 회귀값은 [`기능_명세.md`](../명세/기능_명세.md), 테스트 대상과 실행 순서는
[`개발_계획.md`](../설계/개발_계획.md)를 따른다.

## 2. 최상위 원칙

모든 코드가 아니라, 깨졌을 때 문제가 되는 기능 계약과 기술 위험을 테스트한다.

테스트마다 다음을 설명할 수 있어야 한다.

- 무엇을 보장하는가?
- 어떤 잘못된 변경을 발견하는가?
- 실패하면 사용자나 시스템에 어떤 문제가 생기는가?

코드 커버리지 확보만을 목적으로 테스트를 추가하지 않는다.

## 3. 테스트가 필요한 경우

다음 대상은 위험에 비례해 테스트한다.

- 기능 명세의 입력, 출력, 상태 변화와 오류
- 계산, 정규화, 시간대, 반올림과 경계값
- 인증, 인가, 소유권과 비밀정보 보호
- 트랜잭션, 데이터 제약, 멱등성과 동시 요청
- DB·Redis·migration 등 실제 인프라 동작
- 외부 시스템 장애와 계층 사이의 연결
- 과거에 발생한 결함의 재발

규칙 없는 getter·setter, 프레임워크 자체 동작, 이미 충분히 검증된 단순 위임과 구현 세부사항은
별도로 테스트하지 않는다.

## 4. 작성 원칙

- **행동 검증**: 내부 구현보다 반환값, 오류, HTTP 응답과 저장 상태를 확인한다.
- **하나의 목적**: 한 테스트는 하나의 실패 이유를 갖는다. 같은 목적의 여러 단언은 허용한다.
- **적절한 수준**: 목적을 증명하는 가장 작고 대표성 있는 테스트 수준을 선택한다.
- **충분한 단언**: 테스트 이름이 주장하는 결과와 최종 상태를 실제로 확인한다.
- **대표 사례**: 정상, 경계와 실패 사례 중 서로 다른 결함을 잡는 값만 선택한다.
- **독립성**: 실행 순서, 현재 시각, 로캘과 다른 테스트 데이터에 의존하지 않는다.
- **중복 방지**: 하나의 계약을 여러 계층에서 같은 내용으로 반복하지 않는다.
- **보안**: 테스트 코드, 응답, 로그와 실패 메시지에 실사용 정보와 비밀정보를 남기지 않는다.
- **회귀 기준**: 실패를 숨기기 위해 단언을 약화하거나 기대값을 구현에 맞추지 않는다.

## 5. 테스트 수준

| 수준 | 주된 책임 |
|---|---|
| Unit | 계산, 변환, 정규화와 도메인 규칙 |
| MVC Slice | 요청 검증, HTTP 상태와 오류 응답 |
| Integration | 실제 MySQL·Redis의 쿼리, 제약, 트랜잭션과 장애 처리 |
| E2E | 핵심 사용자 흐름과 계층 연결 |
| Docker Smoke | 이미지, 설정, healthcheck와 실제 기동 |

실제 인프라의 의미가 검증 대상이면 mock이나 대표성이 낮은 대체물로 바꾸지 않는다.

## 6. 작성과 리뷰

- `@DisplayName`에 조건, 행동과 기대 결과를 드러낸다.
- 주석은 무엇을 검증하는지가 아니라 왜 필요한지 설명한다.
- mock은 외부 경계를 제어할 때만 사용하고 검증 대상의 규칙을 다시 구현하지 않는다.
- 변경 코드와 가까운 테스트부터 실행하고 검증 범위를 확장한다.
- 통과, 실패, 미실행 검증과 남은 위험을 구분해 보고한다.

리뷰할 때는 테스트의 목적, 단언의 충분성, 수준의 적절성, 중복과 구현 결합 여부를 확인한다.
