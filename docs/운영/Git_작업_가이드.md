# 오케어 백엔드 Git 작업 가이드

## 1. 문서 목적

이 문서는 오케어 백엔드 과제의 변경 검토, 스테이징과 커밋 규칙을 정의합니다. 커밋할 작업 범위는 [`개발_계획.md`](../설계/개발_계획.md)의 리뷰 경계와 [`작업_계획_가이드.md`](./작업_계획_가이드.md)를 따릅니다.

## 2. 커밋 승인

- 사용자가 `커밋해`처럼 명시적으로 요청하기 전에는 스테이징하거나 커밋하지 않습니다.
- 커밋 전에는 변경 범위, 테스트 결과, `git status`, `git diff`와 Git 사용자 설정을 확인합니다.
- 관련 없는 사용자 변경을 스테이징하거나 되돌리지 않습니다.
- secret, 개인 경로와 도구 전용 설정이 포함되지 않았는지 확인합니다.
- 적용된 Flyway Versioned migration은 수정하지 않고 새 migration으로 전진 처리합니다.

## 3. 커밋 단위

- 커밋 하나는 독립적으로 설명하고 검증할 수 있는 한 가지 목적만 가집니다.
- 기능 코드에는 직접 검증하는 단위·슬라이스·통합 테스트를 같은 커밋에 포함합니다.
- 공개 API, DB, Redis, Docker 실행 절차가 바뀌면 관련 문서를 같은 커밋에 포함합니다.
- 리팩터링과 기능 변경은 리뷰 목적이 다르면 별도 커밋으로 분리합니다.
- 테스트가 실패한 변경과 다른 목적의 변경을 한 커밋에 묶지 않습니다.

## 4. 커밋 메시지

- Conventional Commit 타입은 영문 소문자로 작성합니다.
- 제목과 본문 설명은 한국어로 작성합니다.
- 첫 줄은 `<type>: <한국어 제목>` 형식을 사용합니다.
- 제목 다음에 빈 줄을 두고 변경 내용을 `-` 목록으로 한 항목 이상 설명합니다.
- 본문에는 핵심 구현 내용과 검증 사항을 기록합니다.
- 메시지에 `Co-Authored-By` 트레일러를 넣지 않습니다.

```text
feat: 회원가입 기능 추가

- 이메일 정규화와 중복 검사를 구현
- 비밀번호 BCrypt 해시와 회원가입 테스트를 추가
```

## 5. 커밋 후 확인과 보고

- 생성된 커밋의 해시, 제목과 포함 파일을 확인합니다.
- 커밋에 포함한 범위, 검증 결과와 제외한 변경을 구분해 보고합니다.
