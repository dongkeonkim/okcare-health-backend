# 오케어 백엔드 검증 결과

## 1. 목적과 기준

이 문서는 구현이 기능 계약을 충족하는지 확인하기 위해 실제로 실행한 명령과 최종 관찰 결과를
제공합니다. 검증 범위는 [개발 계획의 테스트 전략](../설계/개발_계획.md#11-테스트-전략), 입력 특성과
기대값은 [기능 명세의 회귀 기준](../명세/기능_명세.md#8-회귀-기준)을 따릅니다.

## 2. 검증 환경

| 항목 | 값 |
|---|---|
| Java | Temurin 17.0.19+10, 컴파일 산출물 major 61 |
| Spring Boot | 3.5.16 |
| Spring Security | 6.5.11 |
| MySQL | 8.4, Testcontainers와 Docker Compose |
| Redis | 7.4.10, `redis:7-alpine` |

## 3. 실행 명령

자동 테스트와 패키징은 Docker가 실행 중인 환경에서 수행했습니다.

```bash
./gradlew clean build
```

Docker 검증은 [README의 실행 절차](../../README.md#실행과-검증)에 따라 `.env.example`을 복사하고
새로 생성한 32바이트 Base64 JWT secret을 설정한 뒤 수행했습니다.

```bash
docker compose up --build -d
docker compose ps
curl --fail http://localhost:8080/actuator/health
```

## 4. 자동 테스트

`./gradlew clean build`가 성공했고 테스트 244건이 모두 통과했습니다.

| 수준 | 건수 | 검증 범위 |
|---|---:|---|
| Unit | 94 | 정규화, 인증, 도메인 규칙 |
| JSON Slice | 24 | fixture 파싱과 응답 직렬화 |
| MVC Slice | 61 | 요청 검증, 인증과 오류 응답 |
| Integration | 65 | MySQL, 리프레시 토큰용 Redis, Flyway와 전체 사용자 흐름 |
| 합계 | 244 | 전체 빌드와 패키징 포함 |

통합 테스트는 다음 경계를 실제 MySQL과 리프레시 토큰용 Redis로 확인합니다.

- 빈 MySQL에 V1·V2·V3 migration 적용
- FK와 UNIQUE 제약조건
- 리프레시 토큰 TTL·회전·폐기
- 건강 데이터 정규화·소유권·멱등 저장
- MySQL 직접 Daily·Monthly 집계와 회귀값
- 가입부터 로그아웃까지 한 세션으로 이어지는 사용자 흐름

## 5. 입력 데이터와 집계

제공된 네 JSON을 실제 정규화 계층에 통과시켜 기능 명세의 입력 특성과 대조했습니다.

| 확인 | 결과 |
|---|---|
| 총 엔트리 | 4,710건 |
| SamsungHealth | 2파일, 2,563건 |
| Apple Health | 2파일, 2,147건 |
| 서로 다른 집계 날짜 | 32일 |
| 입력 특성 | 기능 명세가 정한 8개 항목 전부 일치 |
| 월간 회귀값 | 기능 명세가 정한 8개 행 전부 일치 |

소수점 열두 자리로 정규화한 값이 MySQL에 추가 손실 없이 저장되고 최종 응답 정밀도와 월간 회귀값을
유지하는지 확인했습니다. 정밀도 선택의 수치 근거는
[개발 계획의 저장 설계](../설계/개발_계획.md#62-숫자와-시간-타입)에 있습니다.

월간 값은 반올림 전 원본 행을 직접 집계한 뒤 응답에서 반올림했습니다. 일별로 반올림한 값을 월간으로
합치면 기능 명세의 회귀값과 어긋나는 것을 테스트로 고정했습니다. UTC 날짜와 서울 날짜가 다른 Apple
Health 엔트리 450건과 월 경계를 넘는 11건도 같은 회귀 대조로 검증했습니다.

실제 Daily·Monthly 응답 값은 [조회 결과](./조회_결과.md)에 있습니다.

## 6. Docker API 검증

### 6.1 기동과 migration

| 확인 | 결과 |
|---|---|
| 컨테이너 | `app`·`mysql`·`redis` 모두 `healthy` |
| Actuator | `200`, 종합 상태 `{"status":"UP"}`만 반환 |
| 빈 볼륨 | MySQL·Redis 볼륨 재생성 |
| Flyway 이력 | V1·V2·V3 순차 적용 성공 |
| 이메일 콜레이션 | `utf8mb4_0900_as_cs` 유지 |
| `record_key` 타입·비교 | `VARCHAR(255)`, 대소문자·악센트 구분 |

빈 MySQL 전체 migration 적용은 `FlywayMigrationTest`와 실기동 MySQL의 Flyway 이력으로 확인했습니다.
`record_key`의 타입과 콜레이션은 `information_schema`에서 대조했습니다.

### 6.2 인증

| 요청 | 결과 |
|---|---|
| 회원가입 | `201` |
| 같은 이메일 재가입 | `409` |
| 대소문자·앞뒤 공백만 다른 이메일 로그인 | `200` |
| 틀린 비밀번호·등록되지 않은 이메일 로그인 | 모두 `401`, 본문 의미 동일 |
| 토큰 재발급 | `200`, 리프레시 토큰 `jti` 회전 |
| 교체된 토큰 재사용 | `401` |
| 로그아웃 | `204` |
| 로그아웃한 리프레시 토큰 재사용 | `401` |
| 로그아웃 후 기존 액세스 토큰으로 조회 | 자체 만료 전까지 `200` |

Redis에는 리프레시 토큰의 SHA-256 해시만 저장됐습니다. TTL은 1,209,600초였고 재발급 후 기존 키가
삭제됐으며 로그아웃 후 대상 키가 사라졌습니다.

### 6.3 저장과 멱등성

| 요청 | 결과 |
|---|---|
| 인증 없이 저장 | `401` |
| 네 JSON 순차 저장 | 모두 `200`, `received`와 `inserted` 일치 |
| 같은 JSON 재전송 | 신규 행 없이 `duplicated`만 증가 |
| 측정값 한 건 변경 | `updated=1` |
| 가변 길이 `recordkey` 저장 | `200`, 입력과 같은 `recordkey` 응답 |
| 대소문자만 다른 `recordkey` 2건 저장 | 모두 `200`, 연결 2건으로 구분 |
| 요청 안의 동일 식별자 중복 | 마지막 값 저장, 결과 건수는 식별자 기준 계산 |
| 같은 회원의 동일 `recordkey` 동시 저장 | 양쪽 `200`, 저장 행 증가 없음 |
| 다른 회원의 `recordkey`로 저장 | `409` |
| 지원하지 않는 단위 | `400` |

네 입력 파일 저장 직후 MySQL의 활동 레코드는 4,710건, 연결은 4건이었습니다. 대소문자 구분 검증용
레코드 2건을 추가한 최종 상태는 활동 레코드 4,712건, 연결 6건이었습니다. 소수점 열두 자리로 다시
변환했을 때 값이 달라지는 행은 없었으며 FK 제약조건은 고아 행 저장을 거부했습니다.

### 6.4 조회와 소유권

| 요청 | 결과 |
|---|---|
| 61일 Daily 조회 | `200`, 빈 날짜를 포함한 61개 항목 |
| Monthly 조회 | `200`, 기능 명세의 회귀값 8행과 일치 |
| 조회 파라미터·응답 필드 | `recordkey` 사용 |
| 데이터가 없는 날짜·월 | 측정값을 `0`으로 채움 |
| 잘못된 날짜·월 형식과 역전 범위 | `400` |
| Daily 366일·Monthly 24개월 초과 | `400` |
| 없는 `recordkey`와 다른 회원의 `recordkey` | 모두 `404`, `code`·`message`·`fieldErrors` 동일 |

일간 쿼리는 `ix_health_activity_records_connection_date`의 `connection_id`와 `activity_date`를
사용했습니다. 월간 쿼리는 연결 식별자로 범위를 좁혀 전체 테이블 스캔을 피했습니다. 두 집계 모두
MySQL 원본 레코드를 직접 조회했습니다.

## 7. 회귀 검출력

주요 구현을 의도적으로 변경한 뒤 관련 테스트가 실패하는지 확인하고 원복했습니다.

| 변경 | 검출한 테스트 |
|---|---|
| 리프레시 토큰 해시 대조 제거 | Redis 교체 스크립트 검증 |
| 연결 행 잠금 제거 | 동일 `recordkey` 동시 저장 |
| 소유권 조회의 회원 조건 제거 | 소유권과 월간 회귀 검증 |
| 집계값 조기 반올림 | Daily·Monthly 회귀 검증 |
| 실행 계획에서 인덱스 사용 금지 | 실제 선택 인덱스 검증 |

모든 변경을 원복한 뒤 최종 변경을 포함한 전체 244건이 통과했습니다.

## 8. 알려진 환경 문제

### 8.1 Flyway 지원 범위 경고

Flyway 11.7.2는 MySQL 8.4가 검증된 지원 범위보다 새롭다는 경고를 남깁니다. 빈 MySQL, 기존 V1
볼륨의 V2 적용, 전체 통합 테스트와 Docker 재기동은 성공했습니다.

### 8.2 베이스 이미지 메타데이터 해석 지연

macOS에서 `docker compose build`가 `load metadata for eclipse-temurin` 단계에 머무는 경우가 있었습니다.
애플리케이션 문제가 아니라 멀티아치 이미지 메타데이터 해석 지연이었으며, README의
[베이스 이미지 선행 pull 절차](../../README.md#실행과-검증)로 해결했습니다. `Dockerfile`에는 플랫폼을
고정하지 않아 다른 아키텍처에서의 이식성을 유지했습니다.
