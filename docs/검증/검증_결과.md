## 2. 공통 실행 명령

```bash
# 단위·슬라이스·통합 테스트와 패키징
./gradlew clean build

# 실행 환경 기동
cp .env.example .env
docker compose up --build -d
docker compose ps

# 기동 확인
curl --fail http://localhost:8080/actuator/health
```

데이터를 보존한 종료와 볼륨 제거를 구분한다.

```bash
docker compose down

# 데이터 제거가 명시적으로 필요한 경우에만 실행
docker compose down --volumes
```

테스트만 남는 방어 수단이다.

**날짜 경계 검증을 이 대조가 겸한다.** UTC 날짜와 서울 날짜가 다른 Apple Health 엔트리가 450건이고
그중 11건이 월을 넘는다. 타임존 처리가 어긋나면 두 달 값이 동시에 틀어지므로 별도 경계 테스트를
두지 않았다.

### 5.4 실행 계획

일간과 월간을 각각 `EXPLAIN FORMAT=JSON`으로 확인했다. `possible_keys`가 아니라 실제로 고른
`key`와 `used_key_parts`를 단언한다.

| 쿼리 | 결과 |
|---|---|
| 일간 | `key=ix_health_activity_records_connection_date`, `range`, `used_key_parts=[connection_id, activity_date]` |
| 월간 | 연결 식별자로 좁혀 들어가고 테이블을 훑지 않음 |

**월간은 복합 인덱스를 단언하지 않는다.** 연·월 그룹핑이 인덱스 컬럼에 함수를 씌워 정렬 이점을
없애고, 월간 요청은 최소 한 달이라 범위 조건이 그 연결의 행을 거의 걸러내지 못한다. 조회 범위를
바꿔가며 실측한 결과다.

| 조회 범위 | 고른 인덱스 | 접근 | 검사 행 | 비용 |
|---|---|---|---:|---:|
| 11~12월 | `uk_..._identity` | ref | 1497 | 222.45 |
| 12월만 | `uk_..._identity` | ref | 1497 | 222.45 |

비용과 검사 행 수가 같으므로 그 상태의 선택은 옵티마이저 tie-break이고, 데이터 양이나 MySQL 판에
따라 달라질 수 있다. 성능 차이가 없는 선택을 단언하면 코드가 옳아도 깨지는 테스트가 된다.

| 결함 | 증상 | 원인 |

세 번째는 코덱스 리뷰가 한 건을 지적했고, 그 지적으로 검사기를 만들어 나머지 한 건을 찾았다.

### 6.2 캐시 동작

| 확인 | 결과 |
|---|---|
| 키 형식 | `health:daily:{recordKey}:{version}:{from}:{to}`, 월간은 `health:monthly:` |
| TTL | 일간 300초 이내, 월간 600초 이내 |
| version 키 | 조회는 만들지 않음. 저장 성공 후에만 증가 |
| 적중 판정 | 캐시를 채운 뒤 `health_activity_records`를 비우고 조회해 같은 값이 나오는지로 확인 |
| **적중과 비적중 응답** | **원문까지 동일** |
| 저장 후 | version이 `1`로 증가하고 새 version 키를 사용. 이전 키는 남아 TTL로 만료 |
| 무효화 후 조회 | 저장한 값이 반영됨 |

적중과 비적중의 원문을 비교하는 단언 하나가 직렬화 왕복, 소수 자리 유지와 정렬을 함께 덮는다.
기능 명세가 캐시 장애 여부에 따라 응답 형식과 집계값이 달라지지 않을 것을 요구하므로 이 성질이
검증 대상이다.

### 6.3 장애 대체

Redis 컨테이너를 실제로 정지한 상태에서 확인했다. 대역으로 예외를 던지게 하면 우리 `catch`가
동작하는 것까지만 확인되고 연결이 끊긴 상황은 검증되지 않는다.

| 확인 | 결과 |
|---|---|
| Redis 정지 중 일간·월간 조회 | `200`, 정지 전 응답 원문과 동일 |
| 소요 시간 | 1.961초 (연결 거부로 즉시 실패, 대기하지 않음) |
| version이 정수가 아닐 때 조회 | `200`, 값 동일 |
| 캐시 값이 JSON `null`일 때 | 비적중으로 처리하고 DB에서 다시 채움 |

공유 Redis 컨테이너를 멈추면 뒤따르는 테스트 클래스가 모두 죽으므로, 이 테스트만 자체 컨테이너를
띄우는 별도 클래스에 둔다.

### 6.4 회귀 검출력 확인

| 망가뜨린 대상 | 실패한 테스트 |
|---|---:|
| 조회 `catch` 제거 (장애 대체 무력화) | 3 |

| TTL 제거 | 6 |
| 저장 후 무효화 호출 제거 | 3 |

마지막 두 항목이 이 경계에서 가장 중요하다. 일곱째는 High 결함을 다시 넣는 것이고, 여덟째는 그
결함을 잡는 테스트가 느린 환경에서 조용히 통과하지 않는지 확인하는 것이다.

### 6.5 이 경계에서 고친 결함

넷 다 테스트가 통과하는데도 검증하지 못하던 자리다. 셋은 기능 명세가 금지한 동작이 실제로
재현되었고, 하나는 테스트가 검증하는 척만 했다.

| 결함 | 심각도 | 증상 | 원인 |
|---|---|---|---|
| version이 정수가 아니면 조회 실패 | — | `500` | `NumberFormatException`이 `DataAccessException`을 빠져나감 |
| 저장 전 값이 새 version 키에 실림 | High | TTL 동안 낡은 값이 후속 조회에도 나감 | 클래스 트랜잭션이 소유권 조회에서 스냅샷을 고정하고 그 뒤 더 새로운 version을 읽음 |
| 캐시 값이 JSON `null`이면 조회 실패 | Medium | `500` | `readValue`가 예외 없이 `null`을 반환 |
| 경쟁 테스트가 시간 초과 시 통과 | Low | 결함이 복원돼도 통과 | 관문 대기의 반환값을 버림 |

두 번째가 이 경계의 핵심이다. 적재 함수를 인자로 받는 구조가 Redis 이중 읽기는 막았지만 MySQL
스냅샷 차원은 덮지 못했다. 집계 서비스의 트랜잭션 경계를 없애면 집계 쿼리가 version을 읽은 뒤 자기
스냅샷을 만들므로, 캐시에 담기는 값이 그 version이 약속한 것보다 새롭거나 같아진다.

### 6.6 미실행

Docker 실기동 캐시 검증은 하지 않았다. Redis 정지까지 포함한 검증을 실제 컨테이너에서 자동
테스트가 수행하며, 실기동 확인은 마지막 경계의 전체 흐름 검증에서 함께 한다.

## 7. 알려진 환경 문제

### 7.1 베이스 이미지 메타데이터 해석 지연

`docker compose build`가 `load metadata for docker.io/library/eclipse-temurin:17-jre` 단계에서
진행하지 않는 경우가 있었다. 원인은 애플리케이션이나 `Dockerfile`이 아니라 멀티아치 매니페스트
해석이며, 다음으로 구분했다.

- 호스트에서 Docker Hub 매니페스트 직접 조회: `200`, 0.7초
- 작은 이미지 pull: 10초 내 성공
- 플랫폼을 지정한 pull: 10초 내 성공

베이스 이미지를 플랫폼을 지정해 먼저 받아 두면 빌드가 정상 완료된다.

```bash
docker pull --platform linux/arm64 eclipse-temurin:17-jdk
docker pull --platform linux/arm64 eclipse-temurin:17-jre
```

`Dockerfile`의 `FROM`에 플랫폼을 고정하지 않는다. 고정하면 다른 아키텍처에서 에뮬레이션으로
실행되어 이식성이 오히려 나빠진다.

## 9. 남은 위험

- 저장은 성공했는데 이어지는 무효화가 실패하면 TTL(일간 5분, 월간 10분) 동안 낡은 값이 나간다.
  저장을 실패로 되돌리면 이미 커밋된 데이터를 클라이언트가 없는 것으로 오해하므로 경고 로그만
  남긴다. 무효화를 캐시 저장소에 맡기는 모든 방식이 공유하는 대가다. version을 MySQL 컬럼으로
  옮기면 사라지지만 개발 계획이 Redis로 정했고 창이 TTL로 닫힌다.
- 이전 version의 캐시 키는 TTL까지 남는다. `KEYS`와 패턴 삭제를 쓰지 않기로 한 직접적 결과다.
- version 키가 사라지면 초기값으로 돌아가고, 그 시점에 남아 있는 초기 version 캐시가 다시 유효해질
  수 있다. 현재 설정에서는 도달할 수 없다. `compose.yaml`이 `maxmemory`를 설정하지 않아 정책이
  `noeviction`이고 version 키에 TTL도 없다. `maxmemory`를 축출 정책과 함께 설정하면 조건이 생긴다.
- 실행 계획을 단언하는 테스트는 환경에 의존한다. `ANALYZE TABLE`로 통계를 갱신해 결정적으로
  만들었지만 MySQL 판이 바뀌면 깨질 수 있다. 깨지면 코드가 아니라 환경을 먼저 봐야 한다.
- 월간 집계가 어느 인덱스를 고르는지는 옵티마이저의 tie-break다. 비용과 검사 행 수가 같으므로
  데이터 양이 달라지면 선택이 바뀔 수 있고, 성능 차이는 없다.
- 같은 `recordkey`의 최초 저장이 동시에 세 번 이상 겹치고 그중 승자가 되돌아가면, 한 번뿐인 재시도도
  같은 UNIQUE 위반을 받아 `500`이 된다. 재시도 횟수를 늘려도 같은 틈은 남으므로 늘리지 않았다.
- 저장은 `steps`만 받는다. 집계가 지표를 구분하지 않아 다른 `type`이 같은 기간에 들어오면 두 배로
  계산되기 때문이다. 다른 지표를 받으려면 집계 쿼리와 인덱스에 지표 구분을 먼저 넣어야 한다.
- 서블릿 인증 API, 역할 기반 인가, 비동기나 `ERROR`·`FORWARD` dispatch를 도입하면 현재 휴면
  상태인 Spring Security 기본값이 외부 동작으로 바뀔 수 있다. 특히 인가를 Spring Security로
  옮기면 `AccessDeniedHandler`를 오류 응답 형식에 맞춰 함께 넣어야 한다.
- 로그인 실패의 응답 시간은 균등화하지 않는다. 등록되지 않은 이메일은 비밀번호 비교를 건너뛰므로
  응답 시간 차이가 남는다. 응답 내용 비노출은 충족한다.
- `.env.example`의 JWT secret은 저장소에 공개된 고정값이다. 복사해 그대로 기동하면 알려진 키를
  사용한다.
